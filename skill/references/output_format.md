# 답변 출력 포맷

검색 결과를 근거로 아래 5개 섹션(Markdown)으로 답한다. 사례에 없는 내용은 만들지 않는다.

## 렌더링 규칙 (화면 정렬·접두사)

- 보고서 제목·구분선에 `━`, `─`, `=` 같은 **고정폭(반복 문자) 구분선을 쓰지 않는다.** 채팅 화면 폭에 맞춰 자동 정렬되지 않아 줄이 깨져 보인다. 제목은 Markdown 헤더(`#`, `##`)로만 표기한다.
- 배너형 제목 블록(구분선으로 둘러싼 타이틀) 대신, 최상단에 `##` 헤더 한 줄로 제목을 쓴다.
- 답변 맨 앞에 `model:`, `Model:`, `assistant:` 같은 화자/역할 접두사를 절대 붙이지 않는다. 본문 텍스트로 바로 시작한다.
- 표·목록은 Markdown 표준 문법만 사용하고, 폭을 맞추려고 공백을 수동으로 채우지 않는다.

## ① 상황 요약
현재 요청과 목표를 2~3문장으로 정리. 대상 시스템 민감도(개인정보 포함 여부 등)에 따라 절차가 달라지는 점을 짚는다.

## ② 권장 처리 절차
검색된 상위 사례의 `process_steps` 를 종합해 번호 목록으로 제시. 사례마다 결재선(`approval_route`)이 다르면 "개인정보 포함 시 A→B→정보보호→DBA, 아니면 A→B" 처럼 조건별 분기를 명시한다.

## ③ 준비할 정보 / 문서
`required_documents` 의 합집합과, 검색 결과에서 공통으로 요구되는 확인 정보(대상 시스템, 환경, 사용 기간, 개인정보 여부 등)를 목록으로.

## ④ 주의 사항
- `cautions` 에서 공통적인 항목.
- 반려/보완 후 완료 사례가 있으면, 그 원인(특히 `missing_document`)을 근거로 "처음부터 함께 제출하라"는 식의 실질 조언.
- 데이터 출처 고지("합성/가상 데이터", "사내 규정 확인") 문구는 넣지 않는다.

## ⑤ 참고 사례
검색된 각 사례를 `case_id (상태) — 한 줄 요약` 형태로 나열. 사용자가 특정 사례 상세를 원하면 show_case.py 로 펼쳐 보여줄 수 있음을 안내.

## (선택) 추가 문의처
`related_contact` 가 있으면 맨 끝에 한 줄: `추가 문의: {team} · {contact} · {channel}`.

---

## 담당자 안내 형태 (`weak_match: true` 일 때)

5개 섹션을 쓰지 않는다. 아래 3부분만 짧게:

1. 한 줄 상황: "이 질문에 정확히 맞는 사례가 없습니다." 또는(`directory_only_topic`) "이 요청은 과거 처리 사례로 답할 업무가 아니라 담당 팀에 직접 요청할 사항입니다."
2. 담당자 안내 (반환값 그대로):
   - 담당 팀: `{team}`
   - 연락처: `{contact}`
   - 접수 채널: `{channel}`
   - 이 팀이 맡는 업무: `{note}`
3. 되물을 정보 1~2개 (대상 시스템, 환경, 원하는 값·기간 등).

---

예시(퇴직자 DB 계정 회수)는 실제 검색 결과 SYN-IT-DBA-0232(완료), 0287(완료, 정보보호까지), 0177(보완 후 완료), 0012(진행 중) 기반으로 구성한다.
