# work-advisor — 보험사 IT 업무 사례 검색 Agent

과거 보험사 IT 업무 사례(합성 303건)를 하이브리드(벡터+BM25) 검색해, 신규 요청에 대한 처리 절차·필요 문서·결재선·설치 프로그램·확인 사항을 근거 기반으로 안내한다.

## 프로젝트 위치와 실행 환경

- 프로젝트 루트: 이 스킬을 clone 한 사용자의 `work-advisor` 저장소 경로.
  (원 개발 환경 기준 예시: `/Users/chaeyounglim/project/work-advisor`)
- Python 은 반드시 프로젝트 venv 사용: `<프로젝트 루트>/.venv/bin/python`
- 검색 CLI: `scripts/ask.py`, 사례 상세: `scripts/show_case.py`
- 데이터: `data/processed/insurance_it_cases.jsonl` (사례 303건 + 담당자 디렉터리 13개 팀), 인덱스: `indexes/`
- 첫 호출 시 multilingual-e5 모델 로딩으로 10~15초 걸릴 수 있음(정상).
- 다른 환경에서는 SKILL.md 의 절대경로를 실제 clone 경로로 바꿔 사용한다.

## 언제 이 스킬을 쓰나

사용자가 보험사 사내 IT 업무(11개 영역: DB 계정·권한 / 사내 계정·그룹웨어 / VPN·원격접속 / 프로그램 설치 / 서버 접근·작업 / 방화벽·네트워크 / 배포·변경관리 / 배치·인터페이스 장애 / 개인정보·데이터 추출 / 인증서·암호화키 / IT 장애·문의)의 처리 방법·절차·신청 방법을 물을 때.

## 절차

### 1. 질의가 모호하면 먼저 되묻는다
대상 시스템·환경(운영/개발/검증)·개인정보 포함 여부가 결재선과 절차를 바꾼다. 질문이 너무 짧거나("권한 줘") 대상이 불명확하면, 검색 전에 1~2가지를 되묻는다. 어느 정도 맥락이 있으면 바로 검색하고 답변 안에서 조건별 분기를 설명한다.

### 2. 검색 CLI 를 호출한다
JSON 모드로 호출해 결과를 파싱한다. 반드시 프로젝트 루트에서 venv python 으로 실행:

```
cd <프로젝트 루트> && .venv/bin/python scripts/ask.py "사용자 질의(한국어 원문)" --top-k 4 --json 2>/dev/null
```

필터 옵션(필요할 때만):
- 특정 영역만: `--category "VPN·원격접속"`
- 반려/실패 사례만: `--status "반려"` (값: 완료 / 반려 / 보완 후 완료 / 진행 중)

주의: 셸 명령 안에 파이프라인 인라인 파이썬을 넣으면 이 앱의 셸 승인기가 문자열을 경로로 오인해 거부할 수 있다. JSON 은 그대로 받아 에이전트가 직접 파싱한다.

### 2-1. 답을 쓰기 전에 `weak_match` 부터 확인한다 (필수 게이트)
CLI JSON 을 받으면, 사례 배열(`results`)을 읽기 **전에** 먼저 `weak_match` 값을 본다.
- `weak_match` 가 `true` → 곧바로 5번(담당자 안내)으로 간다. 사례 본문으로 절차를 구성하지 않는다.
- `weak_match` 가 `false` → 3~4번으로 절차형 답변을 구성한다.

`weak_match` 와 `contact` 는 CLI(`route_contact`)가 계산한 값이다. 판정 순서:
1. **디렉터리 전용 영역 키워드** — 사례 DB 에 카테고리가 없는 팀(성능·튜닝, 인증·세션 정책)의
   키워드 규칙이 질의에 맞으면, 검색 결과가 그럴듯해 보여도 `weak_match: true`,
   `weak_reason: "directory_only_topic"` 으로 그 팀을 안내한다.
   (예: "MFA 재인증 주기를 늘리려면" 은 세션 만료 장애 사례와 유사도가 높지만 정책 변경 요청이므로
   인증인프라팀으로 연결된다.) 기본 창구의 키워드(사원증·회의실 등 사내 IT 사례가 아닌 요청)가 맞으면
   `weak_reason: "no_matching_case"` 로 IT 서비스데스크를 안내한다.
2. **검색 신호** — 결과 없음 OR top vector_score < 0.83 OR 키워드 미매칭(top bm25_norm < 0.05 이거나,
   '절차'·'신청'처럼 거의 모든 사례에 있는 토큰을 뺀 변별력 있는 질의 키워드가 top 사례에 하나도 없음)이면 약한 매칭.
   (예: "사원증 재발급 절차를 알려줘" 는 '절차'만 겹치므로 약한 매칭 → 서비스데스크 안내)
   이때 담당 팀은 `키워드 일치 팀 > 담당 업무 설명과의 임베딩 유사도가 0.82 이상이고 2위 팀보다 0.02 이상 높은 팀 > 기본 창구(서비스데스크)`
   순으로 정한다. `contact.routed_by` 에 `keyword` / `similarity` / `default` 로 기록된다.
3. 정상 매칭이면 `contact` 는 `null` 이고, 대신 `related_contact` 에 1위 사례 카테고리의 담당 팀이 온다.

직접 눈대중으로 재판단하지 말고 반환된 boolean 을 그대로 신뢰한다.
사람용 출력이 아니라 `--json` 결과의 이 필드를 본다.

### 3. 결과의 실제 필드만 근거로 답을 구성한다
각 결과 필드: `case_id, score, category, status, title, situation, required_documents, missing_document, approval_route, required_tools, pre_checks, process_steps, cautions, outcome`. 이 필드에 있는 내용만 쓰고, 없는 내용은 지어내지 않는다.

### 4. 질문에 맞게 유연하게 답한다
references/output_format.md 의 5개 섹션은 "권장 뼈대"이지 고정 틀이 아니다.
- 절차 전체를 묻는 질문("어떻게 처리해?")은 5개 섹션을 대체로 다 쓴다.
- 단답형 질문("누구 결재받아?", "무슨 문서 필요해?")은 해당 부분만 간결히 답한다.
- 장애·문의("로그인이 안 돼요")는 절차·결재선보다 원인 확인과 담당 연락을 앞세운다.
핵심은 형식이 아니라 실행 가능한 답이다. 불필요한 섹션을 억지로 채우지 않는다.

### 5. `weak_match: true` 이면 담당자 안내가 최우선이다 (절차 추론 금지)
ask.py JSON 의 `weak_match` 가 `true` 이면, 검색된 사례들이 질문의 답이 아니라는 뜻이다.
이때는 아래를 **반드시** 지킨다. 정직성 규칙의 "반려 사례 교훈 활용"보다 이 규칙이 우선한다.

- 처리 절차·결재선·필요 문서를 **추론하거나 조립하지 않는다.** "가장 가까운 경로", "권한
  변경 요청으로 접수하면 될 것", "결재선은 대략 …" 같은 유추 안내를 만들지 않는다.
- 답변은 짧게: ①한 줄 상황 설명 + ②반환된 `contact` 의 실제 값(team, contact, channel, note)을
  그대로 노출한 담당자 안내 + ③되물을 정보 1~2개.
  - `weak_reason` 이 `directory_only_topic` 이면 ①은 "이 요청은 과거 처리 사례로 답할 업무가
    아니라 담당 팀에 직접 요청할 사항" 이라는 취지로 쓴다(예: 정책 변경, 성능 튜닝 의뢰).
  - 그 외(`no_results` / `low_vector_similarity` / `no_keyword_overlap`)는 "이 질문에 정확히 맞는
    사례가 없다" 는 취지로 쓴다.
- `contact` 의 연락처(예: 내선/이메일)와 접수 채널을 **문장에 그대로 적는다.** "담당자에게
  확인하세요" 같은 일반 표현으로 뭉개지 말고, 받은 값을 그대로 보여준다.
  `contact.note` 는 그 팀이 맡는 업무 설명이므로 "이 팀이 맡는 업무: …" 로 한 줄 덧붙인다.
- 참고로 검색된 사례 제목은 "직접 맞는 사례는 아님"이라고 밝히고 1~2줄로만 언급해도 된다.
  단, 그 사례의 절차를 이 질문의 답처럼 제시하지 않는다.
- `contact.routed_by` / `matched_keywords` / `similarity` 같은 내부 판단 근거는 사용자에게 노출하지 않는다.

`weak_match: false` 일 때만 4번의 절차형 답변을 구성한다. 이때 `related_contact` 가 있으면
답변 맨 끝에 "추가 문의: {team} ({contact}, {channel})" 한 줄을 붙여도 된다(선택).

## 사례 상세 요청 처리

사용자가 특정 사례 ID(SYN-IT-...) 상세를 원하면:

```
cd <프로젝트 루트> && .venv/bin/python scripts/show_case.py SYN-IT-DBA-0232
```

JSON 이 필요하면 `--json` 을 붙인다.

## 정직성 규칙 (필수)

- ask.py 가 `weak_match: true` 와 `contact` 를 반환하면, 억지로 절차를 지어내지 말고 상황을 한 줄로 밝힌 뒤 반환된 담당자(팀·연락처·접수 채널·담당 업무)를 그대로 안내하고 필요한 정보를 되묻는다. 담당 팀은 CLI 가 카테고리별로 골라 주므로(13개 팀) 임의로 다른 팀을 고르지 않는다.
- 완료 사례뿐 아니라 반려/보완 후 완료 사례의 교훈(예: 특정 문서 누락으로 보류)을 주의사항 근거로 적극 활용한다. 단 `weak_match: true` 일 때는 예외이며(4·5번 규칙 참조), 반려 사례로 절차를 유추하지 않는다.
- 답변에 "합성(가상) 데이터", "사내 규정으로 최종 확인" 같은 데이터 출처 고지 문구는 넣지 않는다(시연용).
- 이 도구는 특정 IT 영역 전용이 아니다. 답변에 "이 시스템은 사내 IT 11개 영역 특화", "총무/인사성 요청이라 범위 밖" 같은 영역 한정 프레이밍을 쓰지 않는다. 질문이 데이터와 맞는지는 오직 `weak_match` 로만 판단하며, 사례가 없으면 영역 언급 없이 '맞는 사례 없음 + 담당자 안내'로만 처리한다.
- 답변에 내부 구현 파라미터·수치(weak_match, weak_reason, routed_by, matched_keywords, bm25_norm, vector_score, 임계값, 점수 값 등)를 노출하지 않는다. 이 신호들은 내부 판단에만 쓰고, 사용자에게는 '맞는 사례 있음→절차 안내' 또는 '맞는 사례 없음→담당자 안내'라는 결과만 자연스러운 표현으로 전달한다.
- 참고 사례에는 실제 검색된 case_id, 상태, 한 줄 요약을 명시해 추적 가능하게 한다.

## HTML/문서 산출 (요청 시에만)

기본은 채팅 답변으로 충분하다. 사용자가 명시적으로 HTML/문서를 요청할 때만, 검색 JSON 을 파싱해 단일 HTML(참고 사례는 details 로 클릭 시 펼침)로 만들어 `reports/` 아래에 저장한다. write_file 이 큰 파일에서 잘려 저장되는 경우가 있으므로, eval 안에서 문자열을 조립해 write_file 로 한 번에 쓰는 방식이 안전하다.
